# 实现规格解释器

`docs/essay/spec.md` 定义了一门声明式的财务管理语言：词汇表六项，句法一句话。本文回答如何实现它——以三个已有实验为基础，把三个手写解释器收敛成一个**规格解释器**。

## 三个实验已经覆盖的部分

- `examples/cashflow/runway.py`：`cash`、`buffer`、`monthly_expense` 是状态基线，`due_days`、`delay_risk` 是时间规则的参数；输出按月推演、临界延迟天数、最晚行动日期，`--what-if` 是假设推演；
- `examples/installments/installments.py`：`months`、`start` 生成按月一期的时间规则，`received` 是已发生的事实，`remind_days` 是触发参数；输出收款计划、临近提醒、逾期清单；
- `examples/dunning/dunning.py`：`receivables` 是台账事实，`credit_days` 是时间规则，`reason` 是归因；输出风险分级、按业务员聚合的催款通知与汇报邮件。

词汇表六项在这三个脚本里各有落点，剩下的工作只是把它们从三份手写代码里抽出来。

## 三个脚本共享的骨架

它们的执行流程同构：

1. 读入规格：一份 JSON，声明全部事实与规则；
2. 推导状态：以当天为基准，按时间规则算出到期日、逾期天数、风险分级；
3. 求值触发条件：临近到期、超期、余量越线；
4. 按归因生成行动：提醒、催款、理赔、汇报，同一触发因归因不同而分支；
5. 假设推演：改写时间参数，从第二步重跑。

第二步是纯函数——同样的规格与日期，永远得到同样的状态——第五步因此免费；行动只依赖状态与归因，因此可以做成可替换的插件。这两点是解释器设计的主要约束。

## 统一的规格 schema

把三份场景 JSON 收敛为一种结构，分三组字段：

- `facts`：义务列表，每条含主体、金额、责任人与时间规则（账期或到期日、按月周期），可附归因与延迟概率；
- `baseline`：状态基线，如现金、储备线、月固定支出；
- `triggers`：触发条件到行动的映射，行动按归因分支。

以超期催款为例，规格写成：

```json
{
  "facts": [
    {"subject": "客户A货款", "amount": 40, "owner": "业务甲",
     "invoiced_on": "2026-06-18", "credit_days": 60, "reason": "追讨不紧"}
  ],
  "triggers": [
    {"when": "due_within", "days": 15, "do": "remind"},
    {"when": "overdue", "do": "dunning"},
    {"when": "overdue", "reason": "信保覆盖", "do": "claim"}
  ]
}
```

与现有 `dunning.py` 的场景文件相比，字段一一对应，新增的只有 `triggers`——原来写死在代码里的提醒与催款逻辑，变成规格里可声明的条目。现金流导航的场景多一组 `baseline`；分期收款的事实由合同参数按月生成。

## 迁移路径

1. 抽公共库：账期到到期日的推算、按月偏移、风险分级、按责任人聚合、表格输出，三个脚本里已有现成实现，直接合并；
2. 定义 schema 与校验：读入规格先校验词汇，出现未知字段即造新词的信号；
3. 以分期收款为第一个场景接入解释器，输出与现有脚本逐行对齐；
4. 依次迁移超期催款与现金流导航，补齐归因分支与 `baseline`；
5. 假设推演做成解释器的通用开关，对三个场景同时生效，而不是只属于现金流导航。

## 验收标准

- 同一份规格，解释器的输出与三个手写脚本一致；
- 假设推演对三个场景都可用；
- 新增场景只写规格、不改解释器；需要改解释器时，说明词汇表缺了一个词——回到 spec.md 补词汇，再回来实现。

到这一步，spec.md 是语言的定义，解释器是语言的实现，案例是语料。
