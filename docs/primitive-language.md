# 财务管理原语言

本文从案例库（`docs/gallery`）的三个案例与 `examples/` 的三个实验出发，记录一个阶段性的假设：我们要找的财务管理**原语言**，是一门描述钱的义务如何在时间轴上演进、何时触发什么行动的声明式语言。

## 三个场景文件是同一种文本

三个示例的场景文件并排看，是同一种语言的三个句子：

- `runway.py`：`cash`、`buffer`、`monthly_expense` 是状态，`due_days`、`delay_risk` 是时间规则；
- `installments.py`：`months`、`start` 是时间规则，`received` 是状态，`remind_days` 是触发条件；
- `dunning.py`：`receivables` 台账是事实，`credit_days` 是时间规则，`reason` 是归因。

三个脚本做的事情也相同：读入声明，推导状态，按时间条件生成行动——提醒、催款、汇报——再支持修改参数重跑。它们因此可以看作同一个语义解释器的三个手写变体，而那些场景文件则是这门语言目前的语料。

还有一个安静的事实：三个场景里没有一个字段与借贷记账相关。复式记账从未出现，它被降级为状态流转的一种可能输出。

## 语言的定义

财务管理原语言，是一门描述钱的义务如何在时间轴上演进、何时触发什么行动的声明式语言；用它写出的文本称为**规格**。它的词汇表：

1. 事实：已发生的事，如合同签订、开票、回款到账；事实的集合叫台账；
2. 状态：每笔义务所处的位置，如应收、已收、逾期；以及由超期产生的风险分级，如关注、高风险、坏账风险；
3. 时间规则：把义务钉在时间轴上的约束，如账期、按月一期；到期日由账期推算，延迟概率是规则的参数；
4. 触发条件：状态与时间的函数，如临近到期、超期未收；由它们算出临界延迟天数与最晚行动日期；
5. 归因：行动的分支依据，如超期原因——追讨不紧、客户无力偿付、信保覆盖，不同的原因对应不同的行动；
6. 行动：触发后要做的事，如提醒、催款通知、汇报邮件、信保理赔；复式记账的分录只是其中一种，由状态流转自动产生。

归因与假设推演不是一开始就设计出来的，而是从案例里被发现的：造不出「不同原因不同处置」的句子时，缺的是归因；表达不了「如果回款延迟会怎样」时，缺的是假设推演。

它的句法可以概括为一句话：【主体】处于【状态】，按【时间规则】演进；当【触发条件】满足，按【归因】执行【行动】；改写【时间规则】重演一遍（假设推演），得到的是假设路线。三个案例全部能读成这句话。

## 与 Beancount 的对照

Beancount 的词汇表是分录，为记录已发生的事而设计；原语言的词汇表是义务与时间，为管理将发生的事而设计。当初的失败不在语法，而在词汇表选错了。

## 这套语言如何简化工作

同一份台账驱动风险分析、催款通知与汇报邮件；同一份规格驱动按月推演、预警与假设路线。人声明一次事实，其余全是推导。

假设推演的边际成本为零：规格与执行分离，改一个延迟参数重跑，就知道回款晚三十天会怎样——「如果」是免费的。

新需求是新句子：用现有词汇造出一份规格；造不出句子，就造一个新词——归因与假设推演都是这样来的。

澄清需求也有了锚点。AI 把故事压成一份简短的规格，再把规格读回故事，用户确认这句话对不对就够了；AI 不需要懂财务，只需要会造句。

常规行动由系统执行，人只确认规格、处理例外。几百个业务的催款是常规行动，系统替人发。

## 下一步

三个场景文件是语料，三个脚本是三个手写解释器。下一步是把五类原语形式化为统一的规格 schema，写一个解释器运行所有场景；到那时，案例才真正变成语言——案例是语料，原语是词汇，解释器是语法。
