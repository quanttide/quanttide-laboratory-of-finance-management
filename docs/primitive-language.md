# 财务管理原语言

本文从案例库（`docs/gallery`）的三个案例与 `examples/` 的三个实验出发，记录一个阶段性的假设：我们要找的财务管理**原语言**，是一门描述钱的义务如何在时间轴上演进、何时触发什么行动的声明式语言。

## 三个场景文件是同一种文本

三个示例的场景文件并排看，是同一种语言的三个句子：

- `runway.py`：`cash`、`buffer`、`monthly_expense` 是状态，`due_days`、`delay_risk` 是时间规则；
- `installments.py`：`months`、`start` 是时间规则，`received` 是状态，`remind_days` 是触发条件；
- `dunning.py`：`receivables` 台账是事实，`credit_days` 是时间规则，`reason` 是归因。

三个脚本做的事情也相同：读入声明，推导状态，按时间条件生成行动——提醒、催款、汇报——再支持修改参数重跑。它们因此可以看作同一个语义解释器的三个手写变体，而那些场景文件则是这门语言目前的语料。

还有一个安静的事实：三个场景里没有一个字段与借贷记账相关。复式记账从未出现，它被降级为状态流转的一种可能输出。

## 语言的定义

财务管理原语言，是一门描述钱的义务如何在时间轴上演进、何时触发什么行动的声明式语言。它的词汇表：

1. 事实与事件：已发生的事，如合同签订、开票、回款到账；
2. 状态：每笔义务所处的位置，如应收、已收、逾期，未超期、关注、高风险、坏账风险；
3. 时间规则：把义务钉在时间轴上的约束，如账期、到期日、按月周期、预计到账天数、延迟概率；
4. 触发条件：状态与时间的函数，如临近提醒、超期分级、临界延迟天数、最晚行动日期；
5. 行动：触发后要做的事，如提醒、催款通知、汇报邮件、信保理赔，分录只是其中一种。

词汇表中还有两个后来发现的词。一是归因，即超期原因——追讨不紧、客户偿付、信保覆盖——它决定行动的分支；二是假设推演，让同一份规格在修改后的时间参数下重跑。

它的句法可以概括为一句话：【主体】处于【状态】，按【时间规则】演进；当【触发条件】满足，执行【行动】。三个案例全部能读成这句话。

## 与 Beancount 的对照

Beancount 的词汇表是分录，为记录已发生的事而设计；原语言的词汇表是义务与时间，为管理将发生的事而设计。当初的失败不在语法，而在词汇表选错了。

## 这套语言如何简化工作

### 声明一次，处处派生

同一份台账驱动风险分析、催款通知与汇报邮件；同一份场景驱动推演表、预警与假设推演。人只声明一次事实，下游全是机械推导。原始笔记里的诉求——把数据源准备好之后由系统自动发送——正是这个意思。

### 「如果」是免费的

声明式意味着规格与执行分离：改一个延迟参数重跑，就得到沙盘推演。预算做不到这一点，因为预算把结论写死；导航随时能回答如果回款晚三十天会怎样。

### 新场景是新句子，不是新需求

三个案例共用同一套词汇，新增场景就是用现有词汇造句。造不出句子的地方才需要造新词——归因与假设推演正是这样从案例里被发现的。收集场景的工作从提需求变成扩充并检验词典。

### 澄清需求有了锚点

AI 有损压缩的目标不再是一种记账语法，而是一份几十行的声明；反向翻译就是把声明读回故事，用户确认的是这句话对不对，而不是这段代码对不对。AI 不需要懂财务知识，只需要会造句，这正是两步沟通结构能降低门槛的原因。

### 人只处理例外

系统从规格推导所有常规行动，人只在两处介入：入库前确认规格，行动发生时执行——催业务、走理赔、调整路线。几百个业务发不过来的问题，在语言层面直接消失。

## 下一步

三个场景文件是语料，三个脚本是三个手写解释器。下一步是把五类原语形式化为统一的规格 schema，写一个解释器运行所有场景；到那时，案例才真正变成语言——案例是语料，原语是词汇，解释器是语法。

本文是一个假设，随场景收集持续修订。
